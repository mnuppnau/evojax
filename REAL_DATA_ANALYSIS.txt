────────────────────────────────────────────────────────────────────────────────
NATURAL SIMILARITY CLUSTERS IN REAL DATA
────────────────────────────────────────────────────────────────────────────────

The 8 BloodMNIST classes form natural similarity clusters that any generator
must respect. Some classes SHOULD look similar (same cell lineage), while
others are morphologically distinct.

Cluster 1: GRANULOCYTES (multi-lobed nuclei, granular cytoplasm)
  - basophil, eosinophil, neutrophil, immature_granulocyte
  - These share a common granulocyte appearance: segmented/lobed dark nucleus
    with surrounding granular cytoplasm. The distinguishing features in RGB
    are stain color (eosinophil = pink granules, basophil = dark granules,
    neutrophil = pale granules), but in grayscale these collapse to
    subtle intensity differences.

Cluster 2: MONONUCLEAR CELLS (single round nucleus)
  - lymphocyte, monocyte
  - Large round dark nucleus with thin cytoplasm ring.
  - Lymphocytes are smaller; monocytes are larger with kidney-shaped nucleus.

Cluster 3: ERYTHROCYTES (no nucleus)
  - erythrocyte
  - Small, uniform, pale discs with no nucleus (biconcave disc = 
    slightly darker center ring in grayscale).
  - Very low dark_frac and very_dark_frac.

Cluster 4: PLATELETS (tiny fragments)
  - platelet
  - Much smaller than other cells, appear as small dark dots or irregular
    fragments. Brightest overall (highest mean pixel value).

================================================================================
LAYERED APPROACH: CA-DRIVEN CODE DIFFERENTIATION
================================================================================

GOAL: Improve within-code cytoplasm/nuclei generation while increasing
between-code morphological separation, without destroying cross-code
similarities (e.g., all granulocytes should share basic structure).

The fundamental challenge: the CA currently has no visibility into
pixel-level code separation. It tracks adv, MI, entropy, r_sense (feature-
space separation), and shape_div, but NOT the actual between-code pixel
distance that determines visual differentiation.

─── LAYER A: METRIC INFRASTRUCTURE (IMPLEMENTED, ACTIVE) ──────────────────

STATUS: Deployed and logging.

What it does:
  - Added a code_spread circular buffer (10th element) to metric_history
  - Computes spread_short (20-gen) and spread_med (50-gen) slopes via
    least-squares regression
  - avg_code_spread = mean(pop_var) flows from code_pixel_div through
    tell() into the metric history each generation
  - Both slopes are logged to ks_weights.tsv for monitoring

What it provides:
  - The CA can now SEE whether code separation is improving, stagnating,
    or declining. Before Layer A, the CA was completely blind to this.
  - Slope magnitudes from the current run:
    spread_short ~ [-0.002, +0.003] (noisy, generation-level jitter)
    spread_med   ~ [-0.0007, +0.0007] (smoother, trend-level signal)
  - The code_spread values themselves trend:
    1k-5k: 0.069 → 15k-20k: 0.077 → 31k-36k: 0.083
    (improving but still below real data target of 0.100)

Files modified:
  - knowledge_sources.py: initialize_metric_history, update_metric_history,
    compute_metric_slopes (now returns 13 slopes)
  - pgpe_ca.py: tell() passes avg_code_spread to metric history
  - trainer.py: ks_weights.tsv header includes spread_short, spread_med
  - util.py: checkpoint migration pads older metric_history tuples

─── LAYER B: KS SCORING AWARENESS (IMPLEMENTED, DISABLED FOR BASELINE) ────

STATUS: Code exists but spread influence is zeroed out (Layer-A-only mode).
        Will re-enable once baseline behavior is confirmed stable.

What it does:
  - topographic_score() receives spread_short:
    When spread is stagnating (slope < 3e-5), boosts Topographic KS score
    by up to +0.4. This shifts CA weight toward output-space structural
    exploration — the Topographic KS's natural role since it tracks
    per-code D-feature-space centroids.
  - domain_score() receives spread_med:
    Rewards Domain KS when spread is improving (up to +0.2 at slope=1e-4).
    Penalizes when spread is declining (up to -0.15 at slope=-5e-5).
    When "exploit the rules" isn't producing code separation, weight
    shifts away from Domain KS toward Topographic/Historical.

  Calibration (based on observed slope magnitudes):
    - Topographic threshold: 3e-5 (code_spread improvement of ~0.001
      over 20 generations). Dead-band width 6e-5.
    - Domain multipliers: 2000x (improving) and 3000x (declining),
      calibrated so slopes of 1e-4 produce meaningful [0, 0.2] adjustments.

What it achieves:
  - The CA responds to code-spread stagnation by shifting guidance weight.
  - When all codes look identical (spread flat), Topographic KS gets boosted,
    encouraging the CA to suggest parameters that explore output-space
    structure rather than exploiting the current (non-differentiating) rules.
  - When spread is improving, Domain KS is rewarded — "the rules are working,
    keep exploiting them."

Why it's currently disabled:
  - Need a clean baseline to isolate the effect of the weight changes from
    the previous run's w_mi_base/w_sense_base adjustments.
  - Will re-enable once we confirm the base fitness weights produce stable
    training through 50k+ iterations.

Files modified:
  - helper_functions.py: topographic_score(), domain_score() accept
    spread_short/spread_med (currently assigned to _ for no-op)
  - knowledge_sources.py: get_center_guidance(), get_stdev_guidance()
    unpack and pass spread slopes to scoring functions

─── LAYER C: DOMAIN KS PARETO ARCHIVE (PLANNED, NOT IMPLEMENTED) ──────────

STATUS: Design complete, pending Layer B validation.

What it will do:
  - Add code_spread (or a proxy like best_pop_var) as a 5th Pareto
    objective in the Domain KS archive selection.
  - Current Pareto sort: [|adv|, |mi|, -shape_div, |entropy|]
  - Proposed sort:        [|adv|, |mi|, -shape_div, -code_spread, |entropy|]
  - This ensures the 20-solution archive RETAINS solutions that achieved
    higher between-code pixel separation, even if they're slightly worse
    on adv or MI.

Why it matters:
  - Currently, the archive converges to solutions with virtually identical
    code_spread profiles (archive_stdev_diversity = 0.000053 in prior run).
  - Even with Layer B shifting KS weights toward Topographic KS when spread
    stagnates, the archived solutions being blended don't HAVE high-spread
    diversity to offer.
  - Layer C gives the archive actual high-spread solutions to blend toward.

Additional change: _domain_ks_select_index() will get a new branch:
  - Detect code_spread stagnation (spread_med near zero for extended period)
  - Select the archived solution with highest code_spread
  - Priority: collapse > spread_stagnation > adv_stagnation > normal

Dependencies:
  - Need code_spread to flow into update_domain_ks() as a new metric
    (currently not passed — would add as 11th element or replace an
    existing tracked metric)
  - Need to validate that high-spread solutions can coexist on the Pareto
    front with high-adv solutions (5-objective Pareto may be too permissive)

─── LAYER D: DIRECT FITNESS SIGNAL (FUTURE CONSIDERATION) ─────────────────

STATUS: Not planned for immediate implementation.

If Layers A-C are insufficient, consider:
  - A direct code_spread fitness component (rank_normalized, weight ~0.1-0.2)
    that rewards population members whose generated images show higher
    between-code pixel variance.
  - This differs from the existing r_sense (feature-space separation) because
    it operates in raw pixel space, directly targeting the visual signal.
  - Risk: PGPE may find shortcuts (e.g., brightness offsets per code rather
    than morphological differences). Would need to combine with the existing
    brightness-normalization in code_pixel_div.

Alternative: Instead of pixel-space code_spread, use a NUCLEUS-SPECIFIC
  separation metric:
  - Compute dark_frac per code per population member
  - Reward population members where dark_frac varies across codes
  - This directly targets the primary discriminative axis identified
    in this analysis (dark_frac ranges from 0.147 to 0.473 in real data)

─── ARCHITECTURAL CONSIDERATIONS ──────────────────────────────────────────

Why codes converge to similar images:
  1. The HyperNetwork processes discrete code as an embedding lookup, but
     the embedding dimensionality and the HN architecture may not provide
     enough code-conditional capacity to produce distinct weight sets.
  2. PGPE evolves the HN parameters, not the generator directly. If the HN
     maps different code embeddings to similar generator weights, the
     generator produces similar images regardless of code.
  3. The MI loss (Q-head) can be satisfied by subtle statistical patterns
     invisible to the human eye — the Q-head learns to classify based on
     imperceptible noise patterns rather than morphological differences.

What the generator needs to learn (from this analysis):
  - NUCLEUS DIFFERENTIATION: dark_frac spans 0.147 (platelet/erythrocyte)
    to 0.473 (basophil). The generator's current dark_frac range across
    codes is only 0.394-0.435 — nearly flat.
  - CENTER-EDGE CONTRAST: Real cells have C-E diff ranging from -0.311
    (lymphocyte, strong nucleus) to +0.033 (platelet, no nucleus).
    Generated images range only -0.219 to -0.158 — all look like they
    have moderate nuclei.
  - CELL SIZE: Platelets are tiny fragments; erythrocytes are uniform discs;
    lymphocytes have large nucleus-to-cell ratio. This size variation isn't
    captured by the current generator.
