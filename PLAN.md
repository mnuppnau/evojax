# EvoJAX InfoGAN HyperNetwork Evolution — Project Plan

## Section A: Architecture, Problem Space & Work Plan

### A.1 Project Overview

We are evolving InfoGAN hypernetworks using PGPE (Policy Gradient with Parameter-based Exploration) combined with Cultural Algorithms (CA) in the EvoJAX framework. The dataset is **OrganSMNIST** (28x28 grayscale, 11 organ classes). This work is inspired by Goertzel/Rutt's vision of using evolution instead of backpropagation for training generative models.

The core idea: a small **HyperNetwork** (~5k params) generates weights for a larger **Generator** (~700k params). PGPE evolves the hypernetwork parameters, while a **Discriminator** is trained with standard backpropagation. Cultural Algorithms provide an additional layer of accumulated knowledge to guide the evolutionary search.

### A.2 System Architecture

**Key Components:**

1. **PGPE (pgpe_ca.py):** Evolutionary algorithm maintaining a Gaussian search distribution (center vector + stdev vector over ~25k HN params). Each generation samples 256 noise directions, evaluates 512 solutions (center +/- noise), and computes REINFORCE-style gradients. Uses ClipUp optimizer for center updates.

2. **HyperNetwork (convnet.py):** Linearized architecture with multiplicative embeddings. Takes `(layer_id, chunk_id, depth, scale)` integer/float coordinates. Learned embeddings (32-dim) for layer and chunk IDs are multiplied element-wise for interaction, concatenated with geometric features, then linearly projected to chunk weights. ~25k params, chunk_size=512. Compression ratio ~10:1. No non-linear activations — the linear mapping gives PGPE a smooth fitness landscape. N_LAYERS and N_CHUNKS computed dynamically from actual Generator. This is what PGPE evolves.

3. **Generator (convnet.py):** Resize-conv architecture (NOT ConvTranspose). ~240k params (20 parameter layers, features=96). Receives latent vector (63 noise dims + 11 one-hot code dims = 74 total). Dense(74→392) → reshape(7x7x8) → Conv(3x3,96)+GN+tanh → resize(14x14) → Conv(3x3,96)+GN+tanh → Conv(3x3,96)+GN+tanh → resize(28x28) → Conv(3x3,48)+GN+tanh → Conv(3x3,1)+tanh. All 3x3 kernels. Extra depth layer at 14x14. Produces 28x28x1 images in [-1,1]. Weights are generated by the HyperNetwork.

4. **Discriminator (convnet.py/trainer.py):** Trained with Adam (lr=0.0001, b1=0.5, b2=0.999) via backprop. Has real/fake head + Q-network head for mutual information estimation. Uses spectral normalization. Label smoothing: real=0.9, fake=0.05. MI loss weighted at 0.2 in D-step.

5. **Cultural Algorithms (pgpe_ca.py, knowledge_sources.py, belief_space.py):**
   - **Belief Space:** 7-element tuple containing meta-info, 5 Knowledge Sources, and metric history.
   - **Topographic KS:** Stores per-code centroids (11 x 256 feature vectors) updated with momentum. Tracks what each code "looks like" in feature space.
   - **Normative KS:** Stores acceptable ranges for spreads and safety ratios. Penalizes members that violate population norms.
   - **Domain KS:** Pareto front of 20 elite solutions with GAN diagnostic metadata (r_sense, r_cons).
   - **Situational KS:** Single best-ever solution (most exploitative).
   - **Historical KS:** Archive of 40 best solutions across generations.
   - **Metric History:** Rolling buffer (window=100) tracking 8 metrics per generation for slope computation.
   - **CATGAME scoring:** Softmax-weighted KS contribution (vs winner-take-all) for gradient blending.
   - **CA Gradient Blend:** KS-suggested targets are converted to gradient directions, scaled to match REINFORCE gradient magnitude, then blended at 5% weight.

6. **Latent Task (latent.py):** Defines evaluation. Uses shared-z design: `jnp.repeat(z_base, 11, axis=0)` — groups of 11 consecutive samples share same z, differ only by code. Computes r_sense, r_cons, r_intra, normative_penalty.

7. **Trainer (trainer.py):** Main training loop orchestrating D-step (backprop) and G-step (PGPE ask/tell). D-step frequency and freeze threshold control D/G balance.

8. **Simulation Manager (sim_mgr.py):** Threads all metrics through vmapped evaluation of 512 population members in parallel.

### A.3 Training Hyperparameters

- Population size: 512 (256 noise directions, mirrored)
- Batch size: 64
- Max iterations: 290,000
- Center learning rate: 0.0038
- Stdev learning rate: 0.05
- Initial stdev: 0.03
- D optimizer: Adam (lr=0.0001, b1=0.5, b2=0.999)
- Seed: 42

### A.4 Fitness Formula (Current)

All components are rank-normalized to [-1, 1] before weighting:

```
fitness = (rank_normalize(fitness_adv) * w_adv)         # Fool discriminator
        + (rank_normalize(fitness_mi) * w_mi)            # Mutual information
        + (rank_normalize(r_sense) * w_sense)            # Feature-space code separation
        + (rank_normalize(pop_var) * w_div)              # Pixel-space code diversity (brightness-normalized)
        + (rank_normalize(r_intra) * w_intra)            # Within-code variation (use z-noise)
        - (rank_normalize(cons_shortfall) * w_cons_floor) # Penalize centroid drift below floor
        - (rank_normalize(normative_penalty) * w_norm)   # Safety/spread limits
```

**Base weights (CA-modulated):**
| Weight | Base | CA Modulation |
|--------|------|---------------|
| w_adv | 0.53 | +adv_distress (up to +0.2 when D winning) |
| w_mi | 0.10 | Static |
| w_sense | 0.10 | -sense_overshoot (reduce if spiking too fast) |
| w_div | 0.48 | -adv_distress*0.5 (ease off when D crushing) |
| w_intra | 0.20 | +intra_distress (up to +0.15 when codes tightening) |
| w_cons_floor | 0.10 | Static, cons_floor=0.05 |
| w_norm | 0.04 | Scaled by ca_weight |

### A.5 D/G Balance Mechanisms (Current)

1. **D-step frequency:** Every 3rd iteration for first 1,500 iter, then every iteration.
2. **D-freeze threshold:** D params only applied when `real_fake_loss > 0.42`. Prevents D from getting too dominant.
3. **CA activation:** 500-iter warmup, ramps to full over 2,000 iter.

### A.6 Key Metrics (Log Line Order in trainer.py)

Each log block at `log_interval` iterations contains these lines in order:
1. `fitness_adv` — adversarial quality (how well G fools D)
2. `fitness_mi` — mutual information loss
3. `r_cons` — centroid consistency (cosine distance from historical centroids)
4. `r_sense` — feature-space code separation (0.7*min_pair + 0.3*mean)
5. `r_intra` — within-code variation reward (peaks when spread in [0.05, 0.2])
6. `norm_pen` — normative penalty
7. `safety_ratios` — per-code safety ratios
8. `spreads` — per-code spreads
9. `real_fake_loss` — discriminator's classification loss

## Section B: Hypotheses

### B.1 Rank Normalization Prevents Fitness Component Domination
**Hypothesis:** Replacing `standardize()` with `rank_normalize()` on all fitness components prevents any single component from dominating the PGPE gradient, regardless of underlying variance differences.

**Status:** CONFIRMED. This was the single most impactful change. Before rank_normalize, fitness_adv (variance ~0.05) dominated r_sense (variance ~0.009) by 5:1 even with equal weights. Standardize amplified noise when variance was near-zero. Rank_normalize caps all signals to [-1, 1] by rank order.

### B.2 Brightness-Normalized Code Diversity Prevents Brightness Shortcut
**Hypothesis:** The generator will exploit brightness as a trivial way to differentiate codes (5 bright, 6 dark) unless we subtract per-image spatial mean before computing cross-code pixel variance.

**Status:** CONFIRMED. Previous run locked into 5-bright/6-dark split by iter 6k. After brightness normalization, per-code means at iter 7k range from -0.23 to +0.11 with no clustering. Generator forced to find structural/textural diversity.

### B.3 Fixed Weight Schedules Cause Late-Training Divergence
**Hypothesis:** A `transition` ramp that tripled w_sense from 0.1 to 0.3 at iter 195-200k caused brightness extremes and binary mode collapse, because the schedule was designed for one training regime but the dynamics had shifted.

**Status:** CONFIRMED. Removed fixed transition schedule, replaced with CA-driven adaptive weight modulation. The divergence at 200k was directly caused by w_sense tripling on a fixed schedule.

### B.4 CA-Driven Weight Modulation Can Replace Fixed Schedules
**Hypothesis:** Using metric slopes from the belief space (short/medium/long term trends) to adaptively adjust fitness weights will be more robust than fixed schedules, because it responds to actual training dynamics.

**Status:** IMPLEMENTED, PARTIALLY TESTED. The CA computes slopes for fitness_adv, r_sense, r_intra and modulates w_adv, w_div, w_sense, w_intra accordingly. Early results show stable behavior, but long runs needed to confirm it prevents the 200k-type divergence.

### B.5 D-Step Frequency Reduction Gives G Time to Establish Diversity
**Hypothesis:** The discriminator trains with backprop (fast) while the generator uses slow PGPE evolution. If D trains every iteration from the start, D reaches real_fake_loss=0.30 by iter 300, before G can establish any diversity. Reducing D-step frequency in early training gives G breathing room.

**Status:** CONFIRMED. With D every 3rd iteration for first 1.5k: D reaches 0.31 at iter 1500 (vs 0.30 at iter 300 previously). G develops diverse structures by 5-7k instead of mode-collapsing at 1.9-2k.

### B.6 D-Freeze Threshold Prevents D Dominance
**Hypothesis:** Even after the frequency reduction period, D can get too strong in subsequent training. A `real_fake_loss` threshold freezes D updates when it's winning too easily, giving the diversity signals (r_intra, pop_var) time to counteract the adversarial squeeze.

**Status:** SUPERSEDED BY B.9. Binary threshold at 0.42 worked for early training but had a fundamental limitation: freezing D doesn't weaken it, only prevents it from getting stronger. By 70k, D's frozen capability was sufficient to push G toward adversarial noise patterns. Replaced with smooth gradient scaling (B.9).

### B.9 Smooth D Gradient Scaling Prevents Long-Term D Dominance
**Hypothesis:** A binary freeze threshold can't address long-term D dominance because freezing D at its current strength still leaves G struggling against a strong D. Instead, smoothly scaling D's gradients based on real_fake_loss gives D proportional learning: full learning at equilibrium (real_fake_loss >= 0.5), zero learning when dominant (<= 0.35), linear ramp between. This continuously regulates D rather than freezing it, preventing both the early dominance problem and the late-training adversarial artifact problem.

**Status:** IMPLEMENTED, TESTING. Replaces both the binary threshold (B.6) and provides smoother dynamics than the frequency reduction alone (B.5, still active for first 1.5k).

### B.7 r_intra in Fitness Preserves Within-Code Variation
**Hypothesis:** Without explicit reward for within-code variation, the adversarial signal naturally pushes the generator to ignore z-noise (since D doesn't care about z-variation). Adding `rank_normalize(r_intra) * w_intra` to the fitness formula directly counteracts this by rewarding population members that maintain variation across different z-inputs for the same code.

**Status:** IMPLEMENTED, TESTING. w_intra_base=0.20 with CA boost (intra_distress up to +0.15) when codes are tightening. First results show good within-code diversity at 7k but gradual loss by 10k — may need higher w_intra or the raised D-freeze threshold may help.

### B.8 r_cons Floor Prevents Centroid Drift Without Over-Anchoring
**Hypothesis:** Using r_cons as a floor penalty (only penalize when below 0.05) prevents codes from drifting away from their established identities while not over-anchoring and freezing evolution.

**Status:** IMPLEMENTED, NOT YET TESTED IN ISOLATION. cons_floor=0.05, w_cons_floor=0.1.

### B.10 Wider HyperNetwork for OrganSMNIST Capacity
**Hypothesis:** The 48-wide HyperNetwork hidden layers create a severe bottleneck for OrganSMNIST. All 188,889 Generator weights pass through just 48 neurons, limiting the HN to ~48 independent weight patterns. Widening to 96 neurons (33k → 71k params, 5.7x → 2.7x compression) gives the HN enough capacity to express the richer textures and spatial structures OrganSMNIST requires, potentially resolving the corner cropping artifacts and improving fine-grained detail.

**Status:** IMPLEMENTED, ASSESSED. Wider HN improved structural complexity but did NOT resolve corner cropping or missing dark classes (7/8). Generator architecture changes needed (see B.11).

### B.11 Generator Architecture: 3x3 Kernels + Extra Depth Layer
**Hypothesis:** The persistent corner cropping artifacts and missing dark classes (7 & 8) are caused by the Generator's 5x5 conv kernels, which create spatial edge bias on small feature maps. Additionally, the two 5x5 layers (Conv_1 at 14x14, Conv_2 at 28x28) consumed 79% of HN output, creating a parameter distribution imbalance. Replacing all 5x5 kernels with 3x3 and adding an extra depth layer at 14x14 should: (a) eliminate edge artifacts by using smaller receptive fields, (b) reduce total params from 189k to ~127k while adding depth, (c) improve HN compression ratio from 2.7x to 1.8x, (d) ensure all chunk IDs < 100 (previously Conv_1 had 200 chunks, IDs 100-199 had zero one-hot encoding — a hidden embedding degeneracy).

**New architecture:** Dense(74→392) → reshape(7x7x8) → Conv(3x3,64)+GN+tanh → resize(14x14) → Conv(3x3,64)+GN+tanh → Conv(3x3,64)+GN+tanh [NEW] → resize(28x28) → Conv(3x3,32)+GN+tanh → Conv(3x3,1)+tanh

**Parameter breakdown:** Dense: 29,400 | Conv_0: 4,672 | GN_0: 128 | Conv_1: 36,928 | GN_1: 128 | Conv_2 (new): 36,928 | GN_2 (new): 128 | Conv_3: 18,464 | GN_3: 64 | Conv_4: 289 | **Total: ~127,129** (20 parameter layers, 261 HN chunks)

**Status:** IMPLEMENTED, TESTING.

### B.12 Metric and KS Weight Logging for Pattern Analysis
**Hypothesis:** By recording CA-driven adaptive weights (w_adv, w_mi, w_sense, w_div, w_intra, w_cons_floor, w_norm), ks_winner, and metric slopes every iteration, we can discover correlations between KS selection patterns and training dynamics — e.g., does a particular KS consistently win before stability improvements? Does adv_distress spike correlate with D-dominance recovery?

**Logging design:**
- `metrics.tsv`: Written every log_interval with population-level metric statistics
- `ks_weights.tsv`: Written every 100 iterations (buffered) with per-iteration adaptive weights, distress signals, slopes, and KS winner

**Status:** IMPLEMENTED.

### B.13 Linearized HyperNetwork with Multiplicative Embeddings
**Hypothesis:** The non-linear HN (GELU activations) creates a rugged fitness landscape that PGPE cannot navigate at scale. When HN params were increased from 71k to 98k (to support a wider Generator), training mode-collapsed by iteration 2200. The root cause is not dimensionality — PGPE handled 800k direct Generator params on MNIST digits — but the entangled, non-linear Jacobian of the HN. Perturbing any HN parameter causes coordinated, non-linear changes across ALL generated weights. Linearizing the HN (replacing GELU with learned embeddings + single linear projection) makes the Jacobian constant, giving PGPE a fitness landscape as smooth as direct parameter search.

**Architecture:**
- Old: `one_hot(122) → Dense(96) → GELU → Dense(96) → GELU → Dense(512)` (~71k HN params)
- New: `Embed(layer,32) * Embed(chunk,32) → concat(depth,scale) → Dense(512)` (~25k HN params)

The multiplicative `layer_emb * chunk_emb` interaction gives each (layer, chunk) pair a unique representation — unlike one-hot concatenation (additive, no interaction) or GELU (non-linear, entangled). The final Dense projection is linear, so PGPE perturbations produce predictable, proportional changes in generated weights.

**Key properties:**
- N_LAYERS and N_CHUNKS computed dynamically from the actual Generator (no hardcoded limits)
- Compression ratio ~10:1 (25k HN → 240k Generator) vs previous 1.8:1 (71k → 127k)
- All chunk IDs naturally supported (no one-hot degeneracy possible with learned embeddings)

**Status:** IMPLEMENTED.

### B.14 Generator Capacity Increase (features=96, ~240k params)
**Hypothesis:** With the linearized HN, the Generator can safely be widened from features=64 (~127k params) to features=96 (~240k params). The previous attempt at features=96 with the non-linear HN collapsed at iteration 2200 because the ~98k HN params created an impossibly rugged landscape for PGPE. The linearized HN generates the same wider Generator weights with only ~25k smooth HN params.

**New Generator architecture:** Dense(74→392) → reshape(7x7x8) → Conv(3x3,96)+GN+tanh → resize(14x14) → Conv(3x3,96)+GN+tanh → Conv(3x3,96)+GN+tanh → resize(28x28) → Conv(3x3,48)+GN+tanh → Conv(3x3,1)+tanh

**Status:** IMPLEMENTED, awaiting test.

### B.15 Entropy NaN Bug Fix (CA Was Completely Disabled)
**Hypothesis:** The CA belief space was producing all-NaN guidance vectors, causing the entire CA gradient blend to be silently skipped every iteration. Root cause: `pop_entropy` was computed as `sum(-log(mean_disc_logit + 1e-8) * mean_disc_logit)` where `mean_disc_logit` contains raw discriminator logits (can be negative). Taking `log` of negative values produces NaN, which propagated through: entropy buffer → metric slopes (ent_long=NaN) → 3 of 4 KS scoring functions → softmax of [NaN, valid, NaN, NaN] = all-NaN weights → all-NaN guidance → `has_ca_data` guard skips blend.

**Fix:** Apply `jax.nn.softmax()` to convert raw logits to probabilities before computing entropy: `pop_entropy = -sum(softmax(logits) * log(softmax(logits) + 1e-8))`.

**Impact:** This fix activates the entire CA guidance system for the first time. Previously, the NaN guard (lines 920-926 in pgpe_ca.py) was protecting training from crashing but effectively disabling all CA gradient blending. The ks_winner was always 0 (argmax of all-NaN returns index 0 in JAX). Now all 4 KS scoring functions will receive valid entropy slopes, and the CATGAME softmax-weighted KS contributions will actually influence training.

**Note:** `domain_score()` in helper_functions.py has a hardcoded `+ 0.897` bias (line 313) that gives Domain KS a significant advantage even with valid scores. This may need rebalancing once CA is actually active, but we'll assess after seeing how the system behaves with working CA guidance.

**Status:** IMPLEMENTED.

## Section C: Detailed Analysis

### C.1 Rank Normalization (relates to B.1)

**Problem:** With `standardize()`, when a fitness component has near-zero variance (e.g., all population members are equally bad at fooling D early on), the standardization amplifies noise to unit variance. This creates random gradients that dominate meaningful signals from other components.

**Mechanism:** `rank_normalize(x)` sorts values by rank and maps to [-1, 1] linearly. For pop_size=512, the worst member gets -1.0, the best gets +1.0. This guarantees:
- Every component contributes gradients proportional to its weight, never more.
- Near-zero variance doesn't get amplified.
- Outliers don't dominate (unlike standardize where a single extreme member can shift the distribution).

**Trade-off:** Rank normalization discards magnitude information. If fitness_adv varies from -0.8 to -0.7 (small range, all bad), it still maps to [-1, 1] same as if it varied from -2.0 to 0.0 (large range, some good). This means the PGPE gradient treats small improvements the same as large ones within a component.

### C.2 Brightness Shortcut (relates to B.2)

**Problem:** The `code_pixel_div` metric computed as `mean(var(grouped, axis=1))` — variance across 11 codes sharing same z — was being maximized trivially by making some codes bright and others dark. Per-code means locked into a 5-bright/6-dark pattern by iter 6k that persisted through 289k.

**Fix:** Subtract per-image spatial mean before computing cross-code variance:
```python
grouped_centered = grouped - grouped.mean(axis=(2, 3), keepdims=True)
code_pixel_div = mean(var(grouped_centered, axis=1))
```

This forces the variance to come from spatial pattern differences, not overall brightness.

### C.3 D/G Asymmetry Analysis (relates to B.5, B.6)

**Core tension:** D uses backprop (fast learner), G uses PGPE (slow learner). The discriminator can reach strong performance in 300 iterations. The generator needs thousands of iterations to evolve meaningful structure because PGPE explores via population sampling rather than gradient descent.

**Observed dynamics (latest run, Feb 18):**
- Iter 0-1500: D trains every 3rd iteration. real_fake_loss stays high (~0.5+). G explores freely.
- Iter 1500: D at real_fake_loss=0.31. G has basic structure.
- Iter 1600-1800: D every iteration now, but with 0.42 threshold. G develops distinct organ-like shapes.
- Iter 1900-2000: Previously this was where mode collapse hit. With D-step reduction + r_intra, the system navigated through it.
- Iter 4000-7000: Stable equilibrium. real_fake_loss oscillates 0.48-0.58. Good code diversity.
- Iter 7000-10000: Gradual within-code diversity loss. within_code_var dropped from 0.214 to 0.158 (26%). Between-code separation increased (0.275 to 0.410). The generator trades z-variation for code separation.

**Key insight:** When real_fake_loss dips below ~0.40, D is strong enough to squeeze the population into narrow shortcuts, losing z-variation. This was happening with the 0.3 threshold — D was already dominant at 0.36-0.40 but the threshold didn't catch it.

### C.4 CA-Driven Weight Modulation (relates to B.4)

**Mechanism:** `compute_metric_slopes()` returns 9 slope values computed from the metric history rolling buffer:
1. `adv_short` — short-term (last 20) slope of best fitness_adv
2. `mi_short` — short-term slope of best fitness_mi
3. `adv_med` — medium-term (last 50) slope of best fitness_adv
4. `mi_med` — medium-term slope of best fitness_mi
5. `ent_long` — long-term (full window) slope of entropy
6. `sense_short` — short-term slope of best r_sense
7. `intra_short` — short-term slope of avg r_intra
8. `adv_avg_short` — short-term slope of avg fitness_adv (population-wide, not just best)
9. `sense_med` — medium-term slope of best r_sense

**Adaptation rules:**
1. **adv_distress:** If avg fitness_adv is declining (D winning), boost w_adv up to +0.2, reduce w_div by distress*0.5.
2. **sense_overshoot:** If r_sense spiking too fast (divergence precursor), reduce w_sense by up to 0.08.
3. **intra_distress:** If r_intra declining (codes tightening), boost w_intra by up to +0.15.

### C.5 Within-Code Diversity Loss (relates to B.7)

**Problem:** By iter 10k, the generator produces nearly identical images for the same code regardless of z-noise input. The within/between variance ratio halved: 0.777 (7k) → 0.385 (10k).

**Root cause:** The adversarial signal (w_adv=0.53) naturally selects for members that fool D, regardless of z-variation. D doesn't reward z-diversity. So the evolutionary pressure pushes toward ignoring z-noise and producing a single "best" image per code.

**Current mitigation:** r_intra in fitness (w_intra=0.20 + CA boost) + D-freeze at 0.42 + code_pixel_div (w_div=0.48). The question is whether these are strong enough relative to w_adv=0.53.

**File:** `evojax/algo/pgpe_ca.py` (lines 150-156)
**Change:** Added `rank_normalize()` function. Replaced all `standardize()` calls in fitness computation with `rank_normalize()`.
```python
@jax.jit
def rank_normalize(x):
    n = x.shape[0]
    ranks = jnp.argsort(jnp.argsort(x)).astype(jnp.float32)
    return 2.0 * ranks / jnp.maximum(n - 1, 1) - 1.0
```

### G.1 — Feb 18, 2026: Reassessing CA's Role in Training Dynamics

**Context:** With CA now active from iter 500 (previously 115k) and driving adaptive weight modulation, we revisited whether CA is contributing more than originally assessed.

**Previous assessment (CA at 115k):** CA was mostly framework overhead. rank_normalize + code_pixel_div + weight balancing were the primary stabilizers. CA's 5% gradient blend was barely noticeable. Honest conclusion: the system avoided mode collapse due to fitness engineering, not CA.

**Revised assessment (CA at 500, driving weight modulation):** CA is now a meaningful contributor to training stability, specifically through its role as an **adaptive fitness landscape controller**. Two distinct CA contributions:

1. **Metric history + slope computation + weight modulation (impactful):** The belief space accumulates knowledge about training dynamics via a rolling buffer of fitness_adv, r_intra, r_sense trends. When r_intra drops (codes tightening), `intra_distress` fires and boosts w_intra. When avg fitness_adv declines (D dominating), `adv_distress` boosts w_adv and eases w_div. Evidence: the diversity ratio trajectory shows recoveries (e.g., ratio jumping from 0.53 at 12k back to 0.73 at 14k) — signature of an adaptive system correcting itself, not a static system drifting.

2. **5% gradient blend from KS targets (still subtle):** Hard to isolate its effect. Probably still a minor contributor compared to weight modulation.

**Key insight — CA as adaptation to a non-stationary fitness landscape:**

In our system, the fitness landscape is non-stationary because the Discriminator changes every iteration via backprop. What "fools D" at iter 5k differs from iter 10k. The relative importance of fooling D vs. maintaining diversity vs. code separation shifts constantly. A weight vector tuned for iter 5k might be wrong for iter 15k — that's exactly what killed the 289k run with the fixed `transition` schedule.

In standard PGPE, the fitness function is static. PGPE doesn't know or care that D changed. If D suddenly gets much stronger, PGPE's gradient gets dominated by the adversarial signal, and diversity pressures get drowned out.

The CA belief space solves this by acting as a **memory + shift detector + response system**:
- **Memory**: metric history stores 100 generations of trends
- **Shift detection**: slope computation identifies when metrics are declining or spiking
- **Response**: weight modulation changes *what PGPE optimizes for* to match the current landscape

It doesn't change the PGPE algorithm itself — it changes the objective that PGPE is searching against. When D is winning, PGPE needs to care more about fooling D. When codes are tightening, PGPE needs to care more about z-variation. The CA is the layer that makes this adaptation happen.

**Paper framing:** "CA provides a meta-learning layer that adapts the multi-objective fitness evaluation to the non-stationary landscape created by the co-evolving discriminator." This is an honest and specific claim about what CA does in this system, grounded in the original vision of Cultural Algorithms — a population evolving in a changing environment, with accumulated cultural knowledge helping the population adapt faster than pure genetic search alone.

### G.2 — Feb 18, 2026: Adversarial Artifacts at 70k and Smooth D Regulation

**Observation:** At 60-74k iterations, image quality degraded from smooth organ-like structures to high-frequency checkerboard/noise patterns. This is a new failure mode — not mode collapse (all codes same) but adversarial artifact generation (G finds noise patterns that fool D rather than realistic images).

**Diagnosis:** The binary D-freeze threshold (0.42) has a fundamental limitation: it stops D from getting *stronger* but can't make it *weaker*. Over 70k iterations, D accumulated enough capability that even when frozen, G couldn't fool it with smooth images. G discovered that high-frequency adversarial textures exploit gaps in D's learned features.

Evidence from logs:
- real_fake_loss trend: 0.50 (69k) → 0.44 (71.5k) → 0.33 (73.9k) — steady D dominance
- r_intra crashed to 0.43 at iter 73700 (from ~0.80), then partially recovered to 0.86 by 73800
- spreads collapsed to 0.022 at iter 73700 (from ~0.05)
- Images at 74k show binary noise/checkerboard patterns replacing smooth organ structures

**Solution:** Replaced binary D-freeze with smooth gradient scaling in `train_step_disc`:
```python
d_scale = clip((real_fake_loss - 0.35) / 0.15, 0.0, 1.0)
grads = tree_map(lambda g: g * d_scale, grads)
```
- At real_fake_loss = 0.50 (equilibrium): d_scale = 1.0 (full D learning)
- At real_fake_loss = 0.42 (D slightly ahead): d_scale = 0.47 (half D learning)
- At real_fake_loss = 0.35 (D dominant): d_scale = 0.0 (D frozen)
- Linear ramp between, providing proportional regulation rather than binary on/off

This is a more principled approach than a threshold because D's learning rate is continuously proportional to how much headroom exists. D self-regulates rather than needing an external freeze.

**Broader insight:** The D/G balance problem in evolutionary GANs is fundamentally harder than in standard backprop GANs because G evolves slowly (PGPE population sampling) while D learns fast (gradient descent). Every D regulation mechanism we've tried (frequency reduction, threshold freeze, now smooth scaling) addresses the same root tension. Smooth scaling is the most principled so far because it directly ties D's learning capacity to the current D/G balance.

### G.3 — Feb 19, 2026: Generator Architecture Overhaul and Logging Infrastructure

**Wider HN assessment at 67k:** Training was stable with the 96-wide HN, but two issues persisted: (1) corner cropping artifacts in nearly every generated image, (2) no code matching the dark patterns of real classes 7 & 8 (mean brightness 0.27, 53-55% dark pixels). These are Generator-level issues, not HN capacity issues.

**Root cause analysis:** The 5x5 conv kernels were the primary suspects. On 14x14 and 28x28 feature maps, 5x5 kernels have an effective receptive field that covers a disproportionate fraction of the image, and with SAME padding the border pixels are computed from fewer neighbors than center pixels, creating systematic edge bias. Additionally, Conv_1 (5x5, 64→64) alone required 200 HN chunks — but N_CHUNKS=100 meant chunk IDs 100-199 all received identical zero one-hot embeddings. The HN literally could not distinguish between 50% of Conv_1's weight chunks.

**Architecture changes:** All 5x5 → 3x3, plus an extra Conv+GN+tanh at 14x14 for depth. This reduces total Generator params from 189k to 127k (the extra layer adds depth but 3x3 kernels are 64% smaller than 5x5). Compression ratio improves from 2.7x to 1.8x. Max chunks per layer drops from 200 to 72, eliminating the one-hot degeneracy.

**Logging infrastructure:** Added two TSV log files: `metrics.tsv` (population-level metrics every log_interval) and `ks_weights.tsv` (per-iteration CA adaptive weights, distress signals, slopes, and KS winner, buffered in groups of 100). This enables post-hoc correlation analysis between CA behavior and training dynamics.

### G.4 — Feb 19, 2026: Linearized HN, Generator Capacity Increase, and Entropy Bug Discovery

**Capacity experiment failure:** Attempted to increase Generator features from 64→96 and HN from 96→128 with the non-linear (GELU) HN architecture. Training mode-collapsed by iteration 2200. Metric analysis revealed:
- fitness_adv regressed to initial levels
- D-frequency transition at iter 1500 was devastating (system couldn't recover)
- ks_winner was ALWAYS 0, ent_long was ALWAYS NaN

**Entropy NaN bug — CA was completely dead:** Discovered that `pop_entropy` was computed by taking `log` of raw discriminator logits (which can be negative), producing NaN. This NaN propagated through the entire CA system: entropy buffer → metric slopes → 3 of 4 KS scoring functions → softmax weights → guidance vectors. The existing NaN guard (nan_to_num + isfinite check at lines 920-926) prevented a crash but silently disabled all CA gradient blending. The CA has contributed ZERO influence to training in every run to date. Fixed by applying softmax before entropy computation.

**Key user insight — HN non-linearity is the scaling bottleneck:** User observed that PGPE successfully handled 800k direct Generator parameters on MNIST digits. This proves dimensionality alone isn't the bottleneck — the HN's GELU activations create a folded, entangled fitness landscape that's fundamentally harder to search than the Generator's natural parameter space. The non-linear Jacobian means small HN perturbations cause correlated, unpredictable changes across all generated weights.

- Only ~25k HN params (vs 71k non-linear) despite generating ~240k Generator weights
- Linear mapping: PGPE perturbations produce predictable, proportional output changes
- Multiplicative interaction: each (layer, chunk) pair gets a unique representation without non-linear entanglement
- N_LAYERS/N_CHUNKS computed dynamically from Generator (no hardcoded limits, no one-hot degeneracy)

**Generator capacity increase:** With the smooth landscape from the linear HN, safely increased Generator features from 64→96 (~127k → ~240k params). This was the capacity that collapsed with the non-linear HN at 98k HN params; now achievable with only 25k smooth HN params.

**Three simultaneous improvements in this update:**
1. Linearized HN (smooth PGPE landscape, enables scaling)
2. CA entropy fix (activates CA guidance for the first time ever)
3. Generator capacity increase (96 features, ~240k params)

## Section H: Long-Term Research Vision

This section documents the research trajectory beyond OrganSMNIST. These goals guide architectural decisions in the current work.

### H.1 Motivation: Evolving Generative Models Without Backpropagation

This project is inspired by the Goertzel/Rutt vision (2024 conversation) that InfoGAN's failure to scale to complex problems may be due to backpropagation's limitations, not the architecture itself. Key observations from that discussion:

- InfoGAN successfully learns disentangled latent variables for simple domains (faces, digits) but "no one managed to get that work for really complex stuff"
- "Back prop never converges when you try to train a complex info model. Why does it never converge? Because the architecture sucks or because back prop sucks?"
- "CMAES doesn't care [about vanishing gradients]. So maybe you could use a floating point GA to train an InfoGAN network."
- "Then you could do an InfoGAN style of transformer, which would enable a whole different attention mechanism to work."
- Jim Rutt: "What is the training method that works with any architecture? Evolution."

Our project tests this hypothesis directly: using PGPE (a floating-point evolutionary algorithm) instead of backpropagation to train InfoGAN generators, starting with images (OrganSMNIST) and progressing to text (IMDB).

### H.2 Next Dataset: IMDB Text Generation with InfoGAN Transformer

**Goal:** Apply the evolved InfoGAN framework to text data using the IMDB dataset. The Generator will be a Transformer architecture where the HyperNetwork outputs the attention matrices directly, creating a "hard attention" mechanism.

**Architecture vision:**
- **HyperNetwork** takes coordinate embeddings `(layer_id, head_id, query_pos, key_pos)` and generates attention matrix entries directly
- These attention patterns are NOT computed via learned Q/K projections (standard soft attention) — they are generated by the evolved HN
- The InfoGAN latent variables `z` flow through the HN and modulate the attention patterns
- MI loss ensures different `z` values produce meaningfully different attention structures
- This enables discovering latent variables that control HOW the model attends (e.g., "attend locally vs globally", "attend to syntax vs semantics")

**Why this is "a whole different attention mechanism":**
- Standard Transformer: `input_tokens → learned W_Q, W_K → softmax(QK^T/√d) → weighted sum` (differentiable, designed for backprop)
- Ours: `evolved HN(layer, head, query_pos, key_pos, z) → attention_pattern → weighted sum` (non-differentiable, designed for evolution)
- Evolution can search over discrete/structured attention patterns that backprop cannot differentiate through
- The HN's coordinate-based generation provides structural inductive bias (positional relationships, layer hierarchy)

**How current OrganSMNIST work aligns:**
| Current (images) | Future (text) |
|---|---|
| Conv Generator (~240k params) | Transformer Generator |
| HN coords: (layer, chunk, depth, scale) | HN coords: (layer, head, query_pos, key_pos) |
| HN output: conv weight chunks | HN output: attention matrix entries |
| InfoGAN: adversarial + MI loss | InfoGAN: adversarial + MI loss |
| CA-guided PGPE | CA-guided PGPE |
| Linearized HN (smooth landscape) | Linearized HN (smooth landscape) |

**Why linearization matters even more for attention:** Attention matrices directly control information flow. Small HN perturbations should produce small, predictable changes in attention patterns — not chaotic reorganizations. A linear HN mapping is essential for PGPE to reliably search over attention structures. The multiplicative embedding approach naturally extends: `interaction = layer_emb * head_emb * query_emb * key_emb` gives position-pair-specific attention within each layer-head combination.

**Connection to radically recurrent architectures (Rutt):** If the Transformer has recurrent connections (output feeds back as input), the HN-generated attention patterns create complex recurrent dynamics. Evolution can train this because it doesn't need to backprop through the recurrence — it evaluates the full forward pass and assigns fitness based on output quality, regardless of computational graph complexity.

### H.3 Per-Layer HyperNetworks with Separate PGPE Solvers

**Problem with monolithic HN (even linearized):** PGPE samples one noise vector and perturbs ALL HN params simultaneously. The REINFORCE gradient for any parameter includes noise from every other layer's perturbation. With pop_size=512 in 25-35k dimensions, cross-layer noise overwhelms the signal. This is the root cause of persistent mode collapse across all HN configurations tested.

**Solution — separate PGPE solver per Generator layer group:**
- Each major layer (conv kernel) gets its own small HyperNetwork (~5k params) and its own PGPE solver
- When evaluating layer i's population, all other layers are frozen at their current best
- Fitness difference is purely attributable to layer i's candidate — clean gradient signal
- SNR per solver: sqrt(256)/5500 ≈ 0.003, vs sqrt(512)/25000 ≈ 0.0009 for monolithic (~5x improvement)

**Layer grouping (features=64 Generator):**

| Group | Generator layers | Params | Per-group HN |
|-------|-----------------|--------|-------------|
| 0 | Dense kernel | 24,304 | ~5.5k |
| 1 | Conv_0 kernel | 4,608 | ~5.2k |
| 2 | Conv_1 kernel | 36,864 | ~5.7k |
| 3 | Conv_2 kernel | 36,864 | ~5.7k |
| 4 | Conv_3 kernel | 18,432 | ~5.4k |
| 5 | Conv_4 + biases + GroupNorm | ~3,500 | Direct params |

**Training loop (block coordinate evolution):**
```
for each iteration:
    D-step: train D on best Generator's output (unchanged)
    G-step: for each layer group i:
        candidates = solver_i.ask()           # pop of layer i HN candidates
        for each candidate:
            full_gen_params = assemble(candidate_i, frozen_others)
        fitness = evaluate(full_gen_params)    # full Generator quality
        solver_i.tell(fitness)                 # update layer i's distribution
```

**CA placement:** One shared CA monitors global metrics (adv_distress, sense_overshoot, etc.) and modulates fitness weights (w_adv, w_mi, w_div...) shared by all solvers. Per-layer solvers don't need their own CA — fitness landscape adaptation is a global concern.

**Compute:** 6 groups × 256 pop = 1,536 evaluations/iter (vs 512 currently, ~3x). But each solver converges faster due to ~5x better SNR, so net iterations to convergence should decrease.

**Alignment with Transformer attention matrix vision:** Each `(layer, head)` pair gets its own PGPE solver evolving that head's attention pattern generator. A 4-layer, 4-head Transformer → 16 small solvers. Each head specializes independently — the most natural architecture for evolved hard attention. Coordinates simplify to `(query_pos, key_pos)` per head, with multiplicative interaction `query_emb * key_emb`.

**Implementation scope:**
- `train_organsmnist.py`: Create list of PGPE solvers, one per layer group
- `trainer.py`: Accept list of solvers, implement per-layer G-step loop with frozen-other-layers evaluation
- `convnet.py`: `LayerHyperNetwork` (small, per-layer) + `MultiLayerAdapter` (manages layer groups, assembles full Generator params)
- `pgpe_ca.py`: No structural changes — same class, multiple instances. CA shared across solvers for fitness weight modulation.
